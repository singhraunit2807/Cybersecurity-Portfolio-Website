VoiceOps AI — Voice-Driven Intelligent Scheduling Assistant

VoiceOps AI is an intelligent voice-driven scheduling backend designed to turn natural spoken requests into structured scheduling actions. The system combines speech recognition, LLM-based intent understanding, backend validation, database state management and notification workflows to support dynamic booking, rescheduling and calendar conflict resolution.

Voice AINLPLLMFastAPITwilioGroqSupabasePostgreSQL

System Architecture

Voice Input→Twilio→Groq Whisper→Groq LLaMA→FastAPI→Supabase PostgreSQL→Booking Engine→Notification

1. Voice Input & Communication

A user speaks the request. Twilio handles the voice side, while the backend takes over once the request reaches the application.

2. Speech-to-Text

Whisper turns the voice into text. That gives the rest of the backend something it can actually parse.

Input: natural voice request → Output: transcribed text for downstream NLP processing.

3. Intent & Information Extraction

LLaMA reads the transcript and pulls out the useful pieces: what the user wants, when they want it and any constraints that matter.

4. FastAPI Backend

FastAPI is where the pieces meet. It validates the request, runs the scheduling logic and connects the AI output to the database and notifications.

5. Scheduling State & Validation

Before changing a booking, I check the request and the current schedule. That matters when a user changes their mind or two requests collide.

6. Booking & Rescheduling

Booking and rescheduling use the same state-aware flow. The backend checks what already exists before it writes a new change.

7. Calendar Conflict Resolution

If the requested slot is already taken, the backend catches the conflict instead of creating an overlapping appointment.

8. Supabase PostgreSQL

Supabase PostgreSQL keeps the booking state between interactions, so the next request is not starting from zero.

9. Notification Layer

Once the change is saved, the user gets a confirmation through the communication layer.

End-to-End Workflow

Receive voice request → transcribe speech → extract intent and entities → validate information → check scheduling state → detect conflicts → book or reschedule → persist updated state → generate confirmation → notify the user.

AI Processing Pipeline

I kept speech recognition and language understanding separate. Whisper handles transcription; LLaMA handles the meaning behind the request. interprets the transcript and converts natural language into scheduling-oriented information that the backend can validate and execute.

Backend Engineering Focus

The project is not only a voice interface. Its core engineering focus is reliable orchestration between AI services, REST APIs, scheduling logic, persistent database state and user-facing communication.

AegisMesh — Zero-Bandwidth Emergency Mesh Communication

AegisMesh is an edge-native disaster communication system using ESP32 microcontrollers, LoRa multi-hop routing and GPS telemetry for emergency coordination when conventional connectivity is unavailable. The design focuses on maintaining a communication path through relay nodes instead of depending on a single direct link.

Emergency CommunicationESP32LoRaMulti-Hop MeshGPS TelemetryEdge Systems

System Architecture

Emergency Node→ESP32→LoRa→Multi-Hop Relay→Destination

1. Emergency Node

The emergency endpoint originates a message that needs to travel across an infrastructure-independent communication path. The node is built around an ESP32 controller and the LoRa communication layer.

2. ESP32 Processing Layer

ESP32 acts as the embedded control layer responsible for preparing, handling and forwarding communication data between the emergency endpoint and the LoRa radio path.

3. LoRa Communication

LoRa provides the long-range radio link used to move emergency packets between nodes. The communication model is designed for off-grid operation where conventional internet or cellular connectivity may not be available.

4. Multi-Hop Relay

Relay nodes extend the communication path by forwarding packets toward the destination. This allows the system to operate as a multi-hop network rather than depending only on a single direct transmission.

5. GPS Telemetry

GPS telemetry adds location information to the emergency communication workflow, making the system suitable for coordination scenarios where node position is relevant to the response.

6. Packet Validation

Automated Python validation harnesses evaluate packet behavior and help verify that the communication workflow behaves as expected across the tested scenarios.

7. LOS / NLOS Validation

The validation process includes both line-of-sight (LOS) and non-line-of-sight (NLOS) scenarios to examine communication behavior under different propagation conditions.

8. Node-Failover Recovery

Failover testing evaluates recovery when a relay node becomes unavailable. The multi-hop design is validated for continued communication through the remaining relay path rather than relying on a single node.

9. End-to-End Communication Workflow

Emergency event → ESP32 packet preparation → LoRa transmission → relay-node forwarding → multi-hop propagation → destination reception → packet validation and telemetry handling.

10. Validation Methodology

Python-based automated validation is used to exercise packet behavior, LOS/NLOS communication scenarios and node-failover recovery. This provides a repeatable way to test the communication pipeline instead of relying only on manual observation.

Kernel-Level Runtime Protection — eBPF-AIMES

eBPF-AIMES is an AI-assisted Linux security architecture designed for kernel-level behavioral monitoring, anomaly detection, risk scoring and defensive response. The project focuses on observing low-level system activity through eBPF and moving structured telemetry into user space for security analytics.

SecurityAI/MLeBPFLinuxRuntime ProtectionBehavioral Monitoring

System Architecture

Linux Activity→eBPF Sensors→Event Collection→Feature Extraction→AI/ML Analysis→Risk Score→Defensive Response

1. Linux Activity Capture

The monitoring layer observes security-relevant runtime activity such as process execution, file access and network connections. eBPF probes are intended to capture telemetry close to the kernel with low collection overhead.

Example events: process execution, file open/access, network connect and module-related activity.

2. eBPF Sensors

eBPF programs attach to suitable kernel tracepoints, kprobes or uprobes to observe selected events. The sensor layer keeps raw collection separate from higher-level security analytics.

3. Event Processing

Captured events are filtered, normalized and enriched before being forwarded to user space. eBPF maps or ring buffers can carry structured telemetry from the kernel side to the analysis layer.

Typical telemetry: PID, process name, action/event type, destination, port and timestamp.

4. Feature Extraction

Raw events are transformed into behavioral features that can be consumed by detection logic. Features may represent event frequency, unusual syscall patterns, process relationships, file activity or network behavior.

5. AI/ML Anomaly Detection

The user-space analytics layer can establish behavioral baselines and identify deviations from expected activity. Candidate approaches include Isolation Forest for unsupervised anomaly detection and supervised models such as Random Forest or XGBoost when labeled security data is available.

6. Risk Scoring

Detection signals are converted into a risk score using behavior, context and historical observations. A practical initial policy can classify low-risk activity as normal, medium-risk activity for monitoring, and higher-risk activity for stronger defensive handling.

7. Defensive Response

The response layer is designed to translate security decisions into controlled actions such as alerting, logging, investigation and, where safely implemented, process containment or blocking. Response policies should be validated in a controlled lab before being used for enforcement.

Behavioral Security Model

Instead of relying only on static signatures, eBPF-AIMES is designed around runtime behavior. The system can compare current activity with a learned baseline and use deviations as one input into anomaly and risk analysis.

Security Use Cases

  • Intrusion and suspicious-process monitoring
  • Malware behavior analysis
  • Privileged-access and process activity monitoring
  • Unusual file or system-call behavior detection
  • Network connection and lateral-movement indicators
  • Linux endpoint and runtime security telemetry

End-to-End Implementation Flow

Linux process/file/network activity → eBPF probes → kernel event capture → ring buffer/map transport → user-space event collector → feature extraction → behavioral baseline → anomaly detection → risk scoring → alert/log/controlled response → dashboard and investigation.

Development & Validation Approach

The project can be validated in an isolated Linux security lab using controlled benign and simulated suspicious activity. Detection logic should first run in observe/alert mode, followed by carefully tested enforcement rules. Metrics such as detection quality, false positives, event-processing overhead and response time can be evaluated during implementation.

Project Focus

The core engineering idea is to combine low-level Linux observability through eBPF with user-space AI/ML security analytics, creating a pipeline that can move from raw kernel telemetry to explainable security signals and controlled defensive decisions.
